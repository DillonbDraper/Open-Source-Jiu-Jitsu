* A Second Video Type For OSSBJJ

** Goal: Add an "analysis" tab to the to our app's database component.  This separates out a new kind of video the app can have, dedicated to analysis and studies rather than direct technique instruction.

** Implementation
- Need a new field "type" field on videos to differentiate.  Can be a string key.  Should be a foreign key to a ref table, which can follow the current ref table convention in the application that position, subposition, etc. follow.  That table can be called "video_types".  For now, it just needs two types: instructional and analysis.
  - The migration to create this new field/table should assign all existing videos to the "instructional" type. That should also be the default for the field.
  - The add/edit video form should have a required field for the type.
- To show this in the UI, we should use a tabular interface like we do for the technique_tree and the message tables.  This should have two tabs labeled "Instructional" and "Analysis".
  - Each of those tabs should have a count in parenthesis to their immediate right like the counts in the technique tree.  This will allow the users to see the distribution of video content before they click to change views.  I.E.  If the user is viewing a given specific technique, and there are 3 instructional videos and one analysis video showing it, the tabs should read "Instructional (3)" and "Analysis (1)"
  - The views rendered can be separate live components or part of the same one, whichever is simpler/cleaner.

* Collaborative Plan
** Goal
Add first-class video typing so videos can be categorized as either instructional or analysis, expose the type in video create/edit flows, backfill existing videos as instructional, and render the database video list behind two count-bearing tabs: Instructional and Analysis.

** Current Understanding
- Videos are modeled by =FosBjj.JiuJitsu.Video= in =lib/fos_bjj/jiu_jitsu/video.ex= using Ash/Postgres.
- Existing config/reference tables such as positions and sub-positions use dedicated Ash resources plus =use FosBjj.ConfigData.Schema= and code-defined =@config_values=.
- The app guideline says schema changes should be made by changing Ash resources and running =mix ash.codegen <name>=, not by hand-authoring migrations.
- The current database list lives in =lib/fos_bjj_web/live/database_component.ex= and filters by technique, attire, title search, soft deletion, and pagination.
- Video add/edit UI lives in =lib/fos_bjj_web/live/video_live/video_form_component.ex= and already loads other reference data such as techniques and grips.

** Assumptions
- =instructional= should be the default video type for new videos and for all existing rows.
- =analysis= videos use the same metadata, technique relationships, grip relationships, detail view, reporting, notes, and permissions as instructional videos unless future specs say otherwise.
- Counts in the new tabs should respect the currently selected filters/search context where possible: selected technique, attire filter, title search, and =deleted_at IS NULL=.
- Pagination should apply within the active tab, not across both video types combined.
- The implementation branch/worktree for this plan should originate from =main= or =master= according to the org-plans skill execution rules.

** Questions
- [ ] Should the tab counts include all videos for the current technique/attire/search filters, or should title search be ignored for counts so tabs describe the broader selected technique?
  - They should count for title search, can ignore gi/nogi and count total videos onl.
- [ ] Should URL state include the selected video type tab, e.g. =?video_type=analysis=, so refresh/back/share preserves the active tab?
  - Good question, but no.  Default the instructional tab on navigation.
- [ ] Should non-admin users ever see the type on the video card, or is the tab separation enough?
  - Tab separation is enough.
- [ ] Should the add/edit form use a radio group, segmented control, or combobox for the required video type field?
  - Combobox.

** Risks And Dependencies
- [ ] Ash relationship naming needs to be exact: the =Video= resource should likely store =video_type_name= and =belongs_to :video_type, FosBjj.JiuJitsu.VideoType= using =name= as the destination key.
- [ ] Backfilling and defaults should be represented in Ash-generated migrations; inspect generated migrations before accepting them.
- [ ] Existing tests or fixtures that create videos may fail until they inherit the default or explicitly set =video_type_name=.
- [ ] Adding a second count query path can introduce inconsistency with the video list query if filters diverge.
- [ ] Avoid =String.to_atom/1= on request/user params when adding the type filter; use strings or validated allow-lists.
