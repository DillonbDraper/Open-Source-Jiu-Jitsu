* Action Tab Videos
** Goal: Create InAction Videos accessible from a new "inAction" tab in the main menu.
 - To accomplish this, we need to add a third video type, like we have for technique and analysis currently.
 - We can copy existing patterns directly for how to add a third tab to the UI for this.
 - These "inAction" (camel casing is a reference and intentional for the UI) videos are unique in that they must include a time range as part of the video form
 - The time range should be limited to a length of 15 seconds maximum
 - However, rather than the save putting them into the video table directly, inAction videos should be added to a new table called "in_action_staging".
   This is we will later create a service to clip videos from the range given by the user in the UI.
 - There are two potential ways to handle this from a data perspective: a flag added to the videos table that would hide them in the UI until somehow updated, and then only having an fkey to the in_action_staging table and the time range on the secondary table, or not creating a video record at all and duplicating much of the data onto the new table.  I lean towards the first solution.
 - Our service (not part of this initial batch of work) will eventually cut the videos added of this type and upload them into a bucket of some type (cloudflare r2 or amazon s3).  We don't need to worry about actually handling that right now, but we'll need to add support for playback not from youtube for this type of video. Since we will host these videos ourselves, we will need to use the mishka .video component to play them rather than the iframe pattern currently utilized
 - Notetaking and seeking from notes will also need an expansion to handle for these non-youtube videos, but that can be handled later if we judge it to be too ambition an item in scope to include with this unit of work.

* Collaborative Plan
** Goal
Add durable original-source attribution for hosted inAction clips so the UI can credit and link back to the YouTube video each clip was cut from.

** Current Findings
- [X] Existing creation flow already parses the source YouTube ID in `lib/fos_bjj/jiu_jitsu/in_action_videos.ex`.
- [X] `lib/fos_bjj/jiu_jitsu/in_action_staging.ex` already stores `source_url` and `source_video_id` per inAction video.
- [X] `Video` has a one-to-one `:in_action_staging` relationship, but `lib/fos_bjj_web/live/video_show_component.ex` only loads `techniques`, so source attribution is not available in the public detail UI.
- [X] Hosted playback currently uses `@video.source_type == :hosted` and `@video.hosted_video_url`; normal YouTube videos still use `@video.video_id`.

** Recommendation
Use the existing `in_action_staging` record as the source-of-truth for inAction clip attribution for the first implementation. This avoids an immediate schema migration and preserves existing staged/processed clips. If the team later wants attribution on all hosted videos or wants to decouple public attribution from processing state, add `original_source_url`, `original_source_video_id`, and `original_source_platform` to `videos` via `mix ash.codegen` and backfill from `in_action_staging`.

** Assumptions
- [ ] `in_action_staging` rows are retained after processing and are safe to expose as public metadata.
- [ ] The original source is always YouTube for the current inAction workflow.
- [ ] A link plus visible YouTube ID is sufficient credit for this iteration; channel/title attribution can be added later if desired.

** Questions

- [ ] Should source attribution be shown only on the video detail page, or also in database cards/list rows for inAction videos?

- [ ] Is `in_action_staging` intended to be permanent, or should public attribution move onto `videos` despite requiring a migration?
